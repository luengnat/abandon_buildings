# ฐานข้อมูลโครงการรัฐทิ้งร้างและใช้ประโยชน์ไม่ได้

ฐานข้อมูลภาษาไทยสำหรับติดตามโครงการของภาครัฐ รัฐวิสาหกิจ และองค์การมหาชนที่
สร้างไม่เสร็จ ทิ้งงาน ทิ้งร้าง สร้างเสร็จแต่ไม่ได้ใช้ ใช้ประโยชน์ต่ำ ยกเลิก หรือ
ล้มเหลวในการบรรลุวัตถุประสงค์เดิม

โครงการที่อยู่ระหว่างก่อสร้างหรืออยู่ในขั้นเสนออาจปรากฏในฐานข้อมูลได้ แต่ต้อง
ระบุสถานะให้ตรง ไม่เหมารวมว่าเป็น “อาคารร้าง”

ID 151 เป็น probable จากรายงานภาคสนาม Thai PBS ปี 2569 แต่ยังไม่มีพิกัดแปลง/อาคารหรือสัญญาต้นฉบับ; ID 154 ยืนยันประวัติการถูกทิ้งร้างได้ แต่สภาพปัจจุบันยังไม่ทราบ; ID 152 กำลังปรับปรุง; ID 153 เป็นสัญญาเฉพาะส่วนของท่าเรือปัตตานีที่เชื่อมโยงกับภาพรวม ID 159; ส่วน ID 155 มีบันทึกส่งมอบงานทดแทนตาม Process5 แต่ยังไม่ยืนยันตรวจรับหรือเปิดใช้อาคาร.

รอบทบทวนนี้แยกสัญญาที่ชื่อ/พื้นที่ใกล้กันออกจากสัญญาของอาคารเป้าหมาย: เช่น ID 96 โรงอาหารคนละอาคาร, ID 175 สัญญาที่ผูกกับ อ.รัษฎา ไม่ใช่เบาะแส ต.ช่อง อ.นาโยง, ID 187 สัญญา OTOP คนละโครงการ, ID 247 สัญญาปรับปรุงสถานีภายหลัง และ ID 251 งานขยายเขตไฟฟ้าที่ไม่ใช่อาคารบำบัดน้ำเสีย. ลิงก์เหล่านี้เก็บไว้ใต้หัวข้อ e-GP ที่ตรวจแล้วแต่ไม่ตรง เพื่อให้ตรวจสอบย้อนหลังได้. ตรวจพบ `see_also` อ้างถึง ID ที่ไม่มีอยู่ 0 รายการ; ยังมี self-reference เดิมใน 17 ระเบียนที่อยู่นอกขอบเขต migration นี้.

### เว็บค้นหาและแผนที่

เว็บอ่านข้อมูลจาก `database.json` โดยตรง ไม่ต้องติดตั้งแพ็กเกจเพิ่ม ให้รันจากโฟลเดอร์โครงการ:

```bash
python3 -m http.server 8000
```

แล้วเปิด <http://localhost:8000/web/>. เว็บคัดเฉพาะระเบียนที่มีชื่อหรือประเภทเป็นอาคาร/
สิ่งปลูกสร้าง เช่น อาคารราชการ โรงเรียน โรงพยาบาล สนามกีฬา โรงงาน สะพาน เขื่อน
และระบบบำบัดน้ำ ไม่แสดงระบบ/เส้นทางรถไฟ เรือ/ยานพาหนะ ระเบียนที่เป็นคดีหรือ
เหตุอุบัติเหตุล้วน ๆ และโครงการที่ระบุชัดว่ายังไม่เคยเริ่มก่อสร้าง. ฐาน `database.json`
ยังคงเก็บข้อมูลวงกว้างไว้; การคัดขอบเขตนี้มีผลเฉพาะหน้าเว็บ.

เว็บไม่แสดงระเบียนที่ไม่มี `id` ตามขอบเขตการเผยแพร่ที่เลือกไว้ แต่ไม่ได้ลบแถว
เหล่านั้นออกจาก `database.json`. รายการเรียงตาม ID, เลือกให้รายการที่มีภาพซึ่ง
ยืนยันได้ว่าเป็นสถานที่เดียวกันขึ้นก่อน หรือเรียงชื่อ ก–ฮ ได้; ภาพข่าวเก่าบนการ์ด
มีป้ายเตือนว่าไม่ยืนยันสภาพปัจจุบัน. เมื่อเปิดรายละเอียดจะแสดงภาพประกอบทุกภาพ
พร้อมเครดิตและลิงก์กลับไปยังผู้เผยแพร่. ภาพข่าวที่ใช้เป็นบริบทไม่ใช่หลักฐานว่า
สถานที่ยังทิ้งร้าง.

หมุดสีแดง/เหลืองมาจากพิกัดในระเบียนหรือ e-GP; พิกัดระดับไซต์ที่ยังเป็นจุดประมาณจะแสดงคำเตือน; สีเขียวอมฟ้าเป็นจุดศูนย์กลางตำบล/
อำเภอ/จังหวัดจาก [ชั้นขอบเขตการปกครองของกรมป้องกันและบรรเทาสาธารณภัย](https://gis-portal.disaster.go.th/arcgis/rest/services/MapDX/DPM_TH_Boundary/FeatureServer/3)
ซึ่งใช้เติมตำแหน่งโดยประมาณเมื่อยังไม่มีพิกัดโครงการ. ปัจจุบัน 1 รายการใช้พิกัด
สถานที่จากระเบียนโดยตรง และ 157 รายการใช้พิกัดประมาณระดับไซต์หรือศูนย์กลางพื้นที่; อีก 4
รายการยังไม่มีจุดบนแผนที่. พิกัดประมาณเป็นเพียงบริเวณค้นต่อ ไม่ใช่หมุดอาคารหรือ
แนวเขตที่ดิน; รายการเหล่านี้ระบุระดับความแม่นยำไว้ในรายละเอียดและ popup. หาก
แก้ฐานข้อมูลแล้วต้องสร้างข้อมูลจุดประมาณใหม่ ให้รัน
`node web/build_map_locations.mjs` จากโฟลเดอร์โครงการ. ภาพข่าวมีเครดิตและลิงก์
กลับไปยังผู้เผยแพร่ โดยเว็บไม่คัดลอกไฟล์ภาพมาเก็บใน repository.

เมื่อแก้ไขข้อมูล ให้รันคำสั่งคำนวณใหม่ก่อนแก้ตัวเลขใน README:

```bash
jq '{
  projects: (.projects | length),
  sources: ([.projects[].sources[]] | length),
  cross_references: ([.projects[] | (.see_also // [])[]] | length),
  wikidata: ([.projects[] | select(.wikidata != null and .wikidata != "")] | length),
  sectors: ([.projects[].sector] | unique | length),
  average_description_chars: (([.projects[].description | length] | add) / ([.projects[].description] | length) | round)
}' database.json
```

## วิธีทำงานวิจัย

1. ระบุโครงการและสถานที่ให้แคบที่สุด: ชื่ออาคาร หน่วยงาน จังหวัด อำเภอ และชื่อ
   เดิม/ชื่อใหม่
2. ค้น GovSpending เพื่อหาเลขโครงการ e-GP และรายละเอียดงบประมาณ
3. ตรวจเลขเดียวกันกับ e-GP Process5 โดยตรง
4. เปรียบเทียบชื่อหน่วยงาน งบ ราคาสัญญา วันที่ พิกัด และสถานะสัญญา
5. ตรวจข่าวทางการ รายงาน สตง./กรมธนารักษ์ เอกสารรัฐสภา คำพิพากษา หรือข่าวจาก
   สำนักข่าวที่น่าเชื่อถือ
6. บันทึกผลเป็น `confirmed`, `probable`, `candidate`, `not a match` หรือ
   `unverified`
7. แยกโครงการเดิมออกจากงาน “ส่วนที่เหลือ” หรือ re-tender เสมอ แม้จะเป็นอาคาร
   เดียวกัน

## แหล่งข้อมูลจัดซื้อจัดจ้าง

### GovSpending

```text
https://govspending.data.go.th/home
https://api-govspending.data.go.th/api/get/egp/search
https://api-govspending.data.go.th/api/get/egp/project_detail?project_id=PROJECT_ID&year=BUDGET_YEAR
```

การค้นหาเป็น POST แบบ `application/x-www-form-urlencoded` และต้องส่ง `year`,
`name`, `project_type=3`, `limit`, และ `offset` เมื่อค้นงานก่อสร้าง ตัวอย่าง:

```bash
curl -sS -X POST 'https://api-govspending.data.go.th/api/get/egp/search' \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data-urlencode 'year=2560' \
  --data-urlencode 'name=ค่ายลูกเสือ' \
  --data-urlencode 'project_type=3' \
  --data-urlencode 'limit=100' \
  --data-urlencode 'offset=0'
```

การส่ง JSON body แทน form-urlencoded อาจตอบว่าขาด `year`; อย่าตีความ response
ดังกล่าวเป็นผลค้นหาไม่พบรายการ

### e-GP Process5

```text
https://process5.gprocurement.go.th/egp-agpc01-web/announcement
https://process5.gprocurement.go.th/egp-oann10-service/pb/a-egp-allt-project/announcement/getProjectDetail?projectId=PROJECT_ID
https://process5.gprocurement.go.th/egp-oann10-service/pb/a-egp-allt-project/announcement/getProcurementDetail?projectId=PROJECT_ID
https://process5.gprocurement.go.th/egp-oann10-service/pb/a-egp-allt-project/announcement/getProcureResult?projectId=PROJECT_ID
https://process5.gprocurement.go.th/egp-oann10-service/pb/a-egp-allt-project/announcement/getContractAvailable?projectId=PROJECT_ID
```

หน้า search อาจตอบ WAF หรือ `validateCfTurnTile:false` หากไม่มี session/Turnstile
ที่เหมาะสม นั่นไม่ใช่ผลว่า “ไม่พบโครงการ” ให้ใช้ถ้อยคำว่า “ยังตรวจไม่สำเร็จ”
และตรวจ endpoint รายละเอียดเมื่อมีเลขโครงการอยู่แล้ว

ฟิลด์ที่ต้องแยกจากกัน:

- `projectMoney` — วงเงินโครงการ;
- `priceBuild` — ราคาก่อสร้าง/ราคากลาง;
- `priceAgree` หรือ `contractPrice` — ราคาที่ตกลง/ราคาสัญญา;
- `contractNo`, วันทำสัญญา, วันสิ้นสุด, วันส่งมอบจริง;
- `contractStatus` และ `contprocessName`;
- พิกัดและหน่วยงานเจ้าของโครงการ.

วันที่จาก e-GP มักเป็น ISO UTC (`T17:00:00Z`) ให้แปลงเป็นเวลาไทยก่อนเขียน
รายงาน แต่ควรเก็บค่า raw ไว้ใน working notes หากมีความสำคัญ

## มาตรฐานการยืนยัน

### ระดับความมั่นใจ

| ระดับ | ใช้เมื่อ |
|---|---|
| **confirmed** | เอกสารทางการระบุชื่อ/หน่วยงาน/สถานที่ตรงกันโดยตรง |
| **probable** | ข้อมูลหลายช่องตรงกัน แต่ยังขาดจุดยืนยันสำคัญหนึ่งจุด |
| **candidate** | เป็นผลค้นหาที่มีแนวโน้ม แต่ยังไม่ควรผูกเข้าฐานข้อมูลถาวร |
| **not a match** | ตรวจพบว่าเป็นคนละจังหวัด หน่วยงาน หรือคนละอาคาร |
| **unverified** | ยังไม่มีหลักฐานเพียงพอ |

### การจำแนกสถานะ

ต้องแยกอย่างน้อยระหว่าง:

- ก่อสร้างไม่เสร็จ/หยุดงาน;
- สร้างเสร็จแต่ไม่เคยใช้;
- ใช้งานน้อยหรือไม่ตรงวัตถุประสงค์;
- ทรัพย์สินราชการที่สำรวจว่าไม่ได้ใช้ประโยชน์;
- โครงการยกเลิก/เลื่อน/อยู่ระหว่างเสนอ;
- อาคารที่ยังใช้งานและมีเพียงงานซ่อม;
- ผลค้นผิดรายการหรือชื่อซ้ำ.

สัญญาซ่อมที่ปิดงานแล้วไม่ใช่หลักฐานว่าอาคารร้าง และการไม่พบเลข e-GP จากการ
ค้นหาไม่ใช่หลักฐานว่าไม่เคยมีการจัดซื้อจัดจ้าง

หมายเหตุ: `see_also` เป็นข้อมูลสะสมจากหลาย migration และบางโครงการเก่าไม่มี
ฟิลด์ `id` แยกต่างหาก ตัวเลข cross-reference จึงควรใช้เป็นตัวชี้วัดการเชื่อมโยง
ที่มีอยู่ ไม่ควรตีความว่าเป็นจำนวนลิงก์ที่ resolve ได้สมบูรณ์ 100% จนกว่าจะมีการ
ทำ ID migration แยกต่างหาก

## การแก้ไขข้อมูล

สำหรับการเพิ่มหรือแก้ข้อมูลจำนวนมาก:

1. ค้น `database.json` และตรวจชื่อไทย/สถานที่ก่อน
2. สร้าง `updateN.py` หมายเลขถัดไปที่ยังไม่ใช้
3. ใช้ stable `id` ถ้ามี; ถ้าไม่มีให้จับคู่ด้วยชื่อไทยและสถานที่แบบตรงตัว
4. ทำสคริปต์ให้รันซ้ำได้โดยไม่เพิ่ม URL หรือ cross-reference ซ้ำ
5. คำนวณ metadata ใหม่หลังแก้ไข
6. ตรวจ JSON และดู diff ก่อนส่งมอบ

คำสั่งตรวจขั้นต่ำ:

```bash
python3 -m json.tool database.json >/dev/null
jq '.projects | length' database.json
jq '[.projects[].sources[]] | length' database.json
jq '[.projects[].see_also[]] | length' database.json
```

อย่ารัน `update*.py` ทั้งหมดต่อกันโดยไม่อ่านก่อน เพราะเป็น migration ตามลำดับ
และบางไฟล์อาจเขียนทับ `database.json`

## ข้อควรระวัง

- ห้ามประดิษฐ์เลข e-GP เลขสัญญา งบ พิกัด หรือวันที่
- ห้ามใช้ Wikipedia เป็นหลักฐานเดียวของข้อกล่าวหาเรื่องทุจริตหรือการทิ้งร้าง
- ห้ามเปิดเผย cookie, token, credential หรือไฟล์ session
- ถ้าพิกัดจาก API สลับ latitude/longitude ให้ระบุว่า API ผิดรูปแบบ อย่าแก้เงียบๆ
- ถ้าข้อมูลขัดกัน ให้เก็บข้อขัดแย้งไว้ในคำอธิบายและลดระดับความมั่นใจ
